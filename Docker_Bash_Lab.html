0. Зачем этот лаб и что дальше #

В Traefik Lab был раздел «Введение в Docker: с нуля» — но это была ровно одна страница на весь фундамент, а дальше лаб сразу прыгал в EntryPoint'ы, роутеры и labels. Если после того раздела Docker всё ещё ощущался как набор заклинаний — дело не в вас, а в том, что один раздел физически не может закрыть тему, на которую обычно уходит неделя практики. Этот лаб решает именно это: здесь нет ни Traefik, ни reverse proxy, ни multi-service архитектуры ради архитектуры — только сам Docker, разобранный настолько подробно, насколько это вообще имеет смысл на старте, плюс bash — потому что каждый второй Dockerfile из раздела 9 и почти весь Traefik Lab (entrypoint'ы, healthcheck-скрипты, wait-for-сервисы) написаны именно на нём.

💡 Почему bash идёт параллельно, а не после

Bash в этом лабе — не отдельный курс «сначала выучи язык, потом пиши скрипты». Он вводится ровно в том объёме и в тот момент, когда становится нужен: сначала переменные и exit-коды (чтобы понимать вывод команд), затем условия и циклы (чтобы написать первый entrypoint), затем позиционные параметры и trap (когда понадобится обрабатывать сигналы). К концу лаба вы не будете «знать bash» в полном объёме — но будете уверенно читать и писать 95% того, что встречается в entrypoint-скриптах реальных проектов.

Дальше — трек полностью автономный: всё, что нужно для практики (Node.js-приложение, PostgreSQL, готовые Dockerfile'ы), даётся прямо в разделе 9, отдельно устанавливать ничего не придётся, кроме самого Docker. В разделе 13 в конце — явная точка возврата к Traefik Lab с указанием, какие именно термины оттуда теперь будут понятны без пояснений.

1. Docker с нуля: проблема и модель #

1.1 Проблема, которую решает Docker

Классическая боль: «у меня на компьютере работает, а на сервере — нет». Причина почти всегда в окружении: другая версия языка, не та версия библиотеки, забытая переменная окружения, отсутствующий системный пакет. Docker решает это не тем, что «чинит» окружение, а тем, что убирает саму зависимость от него: приложение упаковывается вместе со всем, что ему нужно для работы — конкретной версией рантайма, библиотеками, файлами конфигурации — в один переносимый пакет (образ). Этот пакет запускается одинаково у вас на ноутбуке, на сервере коллеги и в проде, потому что каждый раз запускается буквально одно и то же, а не «установленное заново по инструкции».

1.2 Контейнер — это не виртуальная машина

💡 Главное отличие

Виртуальная машина (VM) эмулирует целый компьютер: гипервизор создаёт виртуальное железо, на нём ставится полноценная гостевая операционная система со своим ядром — отдельным от ядра хоста. Отсюда вес в гигабайты и старт в десятки секунд. Контейнер — это обычный процесс операционной системы хоста, которому ядро показывает урезанный, изолированный вид системы: свою файловую систему, свою сеть, свой список процессов — как будто он единственный в отдельной коробке. Ядро при этом одно на всех контейнеров — то самое ядро хоста. Отсюда вес в мегабайты и старт за доли секунды.

🔬 Под капотом: как именно ядро Linux создаёт эту иллюзию

Два механизма ядра Linux делают контейнеры возможными, и Docker их не изобретал — он лишь удобно ими управляет:

  • namespaces (пространства имён) — ограничивают, что процесс видит. Есть отдельные namespace для PID (процесс видит только «свои» процессы и себя как PID 1 — вернёмся к этому в разделе 5), для сети (своя таблица маршрутизации, свои интерфейсы), для файловой системы (свой корень /), для хостнейма и для пользователей. Контейнер — это процесс, запущенный в своём наборе namespace'ов.
  • cgroups (control groups) — ограничивают, сколько ресурсов процесс может использовать: CPU, память, диск, сеть. Именно cgroups стоят за флагами вроде --memory и --cpus, которые встретятся в разделе 3.3.

Сам Docker — это удобная обвязка поверх более низкоуровневых инструментов: dockerd (демон) делегирует запуск контейнеров containerd, а тот, в свою очередь, — runc, который непосредственно вызывает системные функции ядра для создания namespace'ов и cgroups. Понимать эту цепочку не обязательно для повседневной работы, но она объясняет, почему «Docker» и «контейнеры» — не синонимы: то же ядро использует и Podman (упомянутый в Traefik Lab), и containerd напрямую в Kubernetes.

1.4 Установка и первая проверка

Если Docker ещё не установлен — на Linux это официальный скрипт curl -fsSL https://get.docker.com | sh (или пакет из репозитория дистрибутива), на macOS и Windows — Docker Desktop. Проверка, что всё работает:

docker version          # версия клиента и демона — если демон не отвечает, покажет ошибку подключения
docker run hello-world  # эталонный "смок-тест": скачивает крошечный образ и запускает его
✅ Если demon недоступен

Ошибка вида Cannot connect to the Docker daemon почти всегда означает одно из двух: служба dockerd не запущена (sudo systemctl start docker на Linux), либо у вашего пользователя нет прав на сокет /var/run/docker.sock (нужно добавить пользователя в группу docker и перелогиниться, либо каждый раз запускать команды через sudo).

2. Жизненный цикл контейнера и основные команды #

2.1 Команды, которые нужны каждый день

# образы
docker pull nginx                    # скачать готовый образ с registry
docker build -t myapp .              # собрать свой образ из Dockerfile в текущей папке
docker images                        # список локальных образов

# запуск контейнера
docker run -d --name web -p 8080:80 nginx
#            │        │      │
#            │        │      └─ проброс порта: локальный:контейнерный
#            │        └─ имя контейнера, чтобы не запоминать ID
#            └─ detached: в фоне, не занимая терминал

# наблюдение и управление
docker ps                            # список запущенных контейнеров
docker ps -a                         # + остановленные
docker stop web                      # мягкая остановка (SIGTERM, потом SIGKILL — см. раздел 5)
docker start web                     # снова запустить существующий (не пересоздавая) контейнер
docker rm web                        # удалить остановленный контейнер
docker rm -f web                     # остановить и сразу удалить

2.2 Отладка живого контейнера

docker logs web              # вывод stdout/stderr контейнера
docker logs -f web           # то же самое, но "хвостом" — как tail -f
docker exec -it web sh       # зайти внутрь работающего контейнера интерактивным шеллом
#           │  │
#           │  └─ имя оболочки; в Debian-based образах обычно есть bash, в Alpine — только sh
#           └─ interactive + tty: полноценный интерактивный терминал
docker inspect web           # весь JSON с метаданными: IP, volumes, env, healthcheck-статус
docker stats                 # живой мониторинг CPU/памяти всех контейнеров, как top
💡 exec — это не "зайти в контейнер", а запустить второй процесс рядом

docker exec не подключает вас к уже работающему процессу контейнера — он запускает новый процесс внутри тех же namespace'ов. Поэтому если внутри контейнера вообще нет шела (бывает в специально урезанных production-образах вроде distroless), docker exec ... sh просто не сработает — шел скачивать неоткуда, файловая система образа не содержит бинарника. Это осознанный компромисс безопасности, с которым вы столкнётесь, если будете гнаться за минимальным размером образа.

2.3 Restart policy — что происходит, если контейнер упал

По умолчанию упавший контейнер просто остаётся в статусе Exited и не перезапускается сам. Это управляется флагом --restart:

ЗначениеПоведение
noпо умолчанию — никогда не перезапускать автоматически
on-failure[:N]перезапускать только если процесс завершился с ненулевым exit-кодом, максимум N раз
unless-stoppedперезапускать всегда, кроме случаев, когда вы сами остановили контейнер (docker stop)
alwaysперезапускать всегда, включая перезагрузку хоста (если демон настроен автозапускаться)

Для долгоживущих сервисов (базы данных, воркеры) в проде почти всегда используется unless-stopped — подробнее в шаге 3.3.

3. Образы и Dockerfile #

3.1 Анатомия Dockerfile

FROM node:20-slim          # базовый образ — с него начинается сборка
WORKDIR /app                # рабочая директория внутри образа; создаётся, если её нет
COPY package*.json ./       # скопировать файлы с хоста в образ
RUN npm install --production # выполнить команду ВО ВРЕМЯ СБОРКИ, результат "запекается" в образ
COPY . .                    # скопировать остальной код
ENV NODE_ENV=production     # переменная окружения, доступная во время сборки и во всех контейнерах из этого образа
ARG BUILD_VERSION=dev        # переменная, доступная ТОЛЬКО во время сборки (пример: docker build --build-arg BUILD_VERSION=1.2)
EXPOSE 3000                  # документирует, какой порт слушает приложение — сам по себе НЕ пробрасывает порт
USER node                    # с этой строки все команды и сам процесс выполняются от пользователя node, не от root
CMD ["node", "server.js"]    # команда по умолчанию при старте КОНТЕЙНЕРА (не сборки)
💡 RUN — это сборка, CMD — это запуск

Самая частая путаница новичков: RUN выполняется один раз, во время docker build, и результат сохраняется в слое образа. CMD ничего не выполняет во время сборки — он просто записывает в метаданные образа, что делать, когда кто-то запустит из него контейнер через docker run. Если поменять только CMD и не пересобрать образ — команда не выполнится, пока не будет запущен новый контейнер.

3.2 Слои и кэш сборки — под капотом

Каждая инструкция Dockerfile (кроме нескольких метаданных-инструкций вроде EXPOSE) создаёт новый слой — неизменяемый diff файловой системы относительно предыдущего слоя. Слои хранятся на диске отдельно и переиспользуются: если два образа имеют одинаковые первые N инструкций, они физически используют один и тот же набор слоёв на диске (технология union filesystem, чаще всего overlay2).

🔬 Под капотом: почему порядок инструкций в Dockerfile определяет скорость сборки

Docker кэширует каждый слой по хэшу инструкции и содержимого. При повторной сборке он идёт по Dockerfile сверху вниз и переиспользует слой из кэша, пока инструкция и её входные данные не изменились. Как только встречается изменившийся слой — кэш всех слоёв ниже сбрасывается, даже если они сами не менялись. Отсюда классическое правило: класть редко изменяющиеся и "тяжёлые" по времени инструкции выше, часто изменяющиеся — ниже.

Наглядный пример — неправильный и правильный порядок для Node.js-проекта:

# ❌ ПЛОХО: любое изменение кода инвалидирует npm install
FROM node:20-slim
WORKDIR /app
COPY . .                     # копируем ВСЁ, включая исходники, которые меняются каждый коммит
RUN npm install               # этот слой пересобирается заново при КАЖДОМ изменении кода — минуты вместо секунд

# ✅ ХОРОШО: npm install кэшируется, пока не меняются package.json/package-lock.json
FROM node:20-slim
WORKDIR /app
COPY package*.json ./         # копируем только манифесты зависимостей
RUN npm install                # этот слой переиспользуется из кэша, пока манифесты не менялись
COPY . .                       # исходники копируются последними — их изменение не трогает слой с npm install

Тот же принцип для PHP/Composer: COPY composer.json composer.lock ./ → RUN composer install → и только потом COPY . ..

3.3 Build context и .dockerignore

Build context — это папка (обычно .), которую docker build целиком отправляет демону перед началом сборки: именно из неё берутся файлы для COPY/ADD. Если в этой папке лежит node_modules на полгига или .git — они тоже уедут демону, даже если ни разу не встречаются в COPY, просто замедляя отправку контекста. .dockerignore работает как .gitignore и исключает такие файлы из контекста:

# .dockerignore
node_modules
.git
.env
*.md
npm-debug.log
✅ Частая ошибка

Забытый .dockerignore с исключённым .env — самый частый способ случайно "запечь" секреты (пароли от БД, API-ключи) прямо в слой образа через COPY . ., откуда их потом можно достать даже из уже собранного образа командой docker history или просто распаковав слои. Секреты передаются через переменные окружения при запуске контейнера (раздел 8), а не копируются в образ.

3.4 COPY vs ADD

ADD умеет две вещи сверх COPY: скачивать файл по URL и автоматически распаковывать локальные архивы (.tar.gz и т.д.). На практике это почти никогда не нужно и часто удивляет неожиданным поведением — общепринятая рекомендация: всегда используйте COPY, пока явно не нужна распаковка архива при копировании.

3.5 Multi-stage build — коротко (подробно в шаге 2.5)

Multi-stage build — это несколько FROM в одном Dockerfile, где поздний стейдж копирует только готовый результат из раннего (например, скомпилированный бинарник), не таща за собой компилятор и инструменты сборки в финальный образ. Подробный рабочий пример — в шаге 2.5, когда уже будет что оптимизировать.

Раз в этом лабе задача — уверенно писать bash-entrypoint'ы, весь практический раздел 9 использует node:20-slim, а не alpine: в Alpine нет полноценного bash по умолчанию, там только sh (реализация BusyBox, по возможностям близкая к dash). Скрипты с #!/bin/bash там просто не запустятся без apk add bash. Это не значит, что Alpine плохой — для production-образов после того, как entrypoint отлажен, переезд на Alpine + apk add bash (если bash-фичи реально нужны) — стандартная практика ради размера.

4. Bash с нуля: параллельный трек #

Это не курс bash "вообще" — это ровно тот набор конструкций, который встречается в 95% entrypoint-скриптов. Цель — не выучить bash как второй язык программирования, а перестать бояться читать и писать 20–40-строчный скрипт, который что-то проверяет, ждёт и запускает основной процесс.

4.1 Shebang и запуск скрипта

#!/usr/bin/env bash
echo "Привет из bash"

Первая строка — shebang — говорит системе, каким интерпретатором запускать файл, если его исполняют напрямую (./script.sh), а не через bash script.sh. #!/usr/bin/env bash находит bash через PATH — это переносимее, чем жёстко прописанный #!/bin/bash, потому что bash не всегда лежит по одному и тому же пути (особенно на macOS с Homebrew). Чтобы запустить скрипт напрямую, у файла должен быть флаг исполняемости:

chmod +x entrypoint.sh
./entrypoint.sh

4.2 Переменные и подстановка команд

NAME="Docker Lab"          # объявление — БЕЗ пробелов вокруг "="
echo "Привет, $NAME"        # использование — с $
echo "Привет, ${NAME}!"     # фигурные скобки — когда сразу за переменной идёт текст без разделителя

CURRENT_DATE=$(date)        # command substitution: результат команды попадает в переменную
echo "Сейчас: $CURRENT_DATE"

echo "Пользователь: $USER, дом: $HOME"   # переменные окружения ведут себя так же, как обычные
💡 Всегда берите переменные в кавычки: "$VAR", не $VAR

Без кавычек bash сначала подставляет значение переменной, а затем ещё раз разбивает результат по пробелам (word splitting) и раскрывает символы вроде *. Если в значении переменной есть пробел (частый случай — пути к файлам), rm $FILE может неожиданно превратиться в удаление нескольких файлов вместо одного. rm "$FILE" всегда безопасен. Это правило без исключений для entrypoint-скриптов.

4.3 Условия и коды завершения

Каждая команда в Unix при завершении возвращает exit code — число от 0 до 255, где 0 значит "успех", любое другое — "ошибка" (конкретное число часто указывает на тип ошибки). Bash хранит код последней выполненной команды в специальной переменной $?:

ls /tmp
echo $?      # 0, если /tmp существует

ls /nonexistent
echo $?      # 2 (или другое ненулевое число) — команда не нашла файл

Условия чаще всего пишут через if и test (короткая форма — квадратные скобки):

if [ -f "/app/config.json" ]; then
  echo "Конфиг найден"
else
  echo "Конфига нет — использую значения по умолчанию"
fi

if [ "$APP_ENV" = "production" ]; then
  echo "Прод-режим"
fi

[ ] — это на самом деле вызов команды test (пробелы вокруг скобок обязательны, это её аргументы). [[ ]] — расширенная конструкция самого bash (не работает в sh/dash), которая безопаснее с непроцитированными переменными и поддерживает &&/|| и сравнение по маске (== с *). Для entrypoint-скриптов, где заранее известно, что интерпретатор — именно bash, [[ ]] — более безопасный выбор по умолчанию.

4.5 Позиционные параметры: $1, $@, $#

#!/usr/bin/env bash
echo "Имя скрипта: $0"
echo "Первый аргумент: $1"
echo "Второй аргумент: $2"
echo "Количество аргументов: $#"
echo "Все аргументы: $@"
💡 "$@" vs $@ — критично для entrypoint-скриптов

Это ключевая конструкция раздела 5: "$@" (в кавычках) разворачивается в список аргументов, где каждый аргумент остаётся отдельным словом, даже если внутри есть пробелы — именно так нужно передавать команду дальше. $@ без кавычек снова попадает под word splitting из пункта 4.2 и может поломать аргументы с пробелами. Правило: в entrypoint-скриптах всегда "$@", никогда голый $@.

Прежде чем переходить к разделу 5, стоит написать (не копировать) вручную такой скрипт и прогнать его локально через bash check.sh production и bash check.sh без аргумента:

#!/usr/bin/env bash
set -euo pipefail

ENV="${1:-development}"

if [ "$ENV" = "production" ]; then

  if [ -z "${DB_PASSWORD:-}" ]; then

Если это читается без запинки и понятно, почему тут ${1:-development}, а не просто $1 — раздел 5 пойдёт легко.

5. ENTRYPOINT vs CMD: где встречаются Docker и Bash #

5.1 Shell form vs exec form

И RUN, и CMD, и ENTRYPOINT можно написать в двух формах:

# shell form — строка выполняется через /bin/sh -c "..."
CMD node server.js

# exec form — JSON-массив, выполняется НАПРЯМУЮ, без промежуточного шела
CMD ["node", "server.js"]
💡 Почему exec form почти всегда правильный выбор

В shell form процесс node запускается как дочерний процесс шела /bin/sh -c, а сам шел становится PID 1 контейнера. В exec form процесс из массива запускается напрямую и сам становится PID 1. Разница критична при обработке сигналов остановки — подробно разберём в шаге 2.4. Практическое правило: CMD/ENTRYPOINT — всегда в exec form (JSON-массив), кроме случаев, когда команде реально нужны возможности шела (переменные, конвейеры) прямо в этой строке.

5.2 CMD и ENTRYPOINT по отдельности и вместе

CMDENTRYPOINT
Назначениеаргументы/команда по умолчаниюосновная программа, которая всегда запускается
Переопределяетсялегко: любой аргумент после docker run imageтолько флагом --entrypoint, редко нужно
Если задан только одинработает как обычная команда запускаработает как обычная команда запуска

Самый полезный паттерн — использовать оба вместе: ENTRYPOINT задаёт скрипт-обёртку, который всегда выполняется первым (проверки, подготовка), а CMD задаёт то, что этот скрипт должен запустить в конце. Тогда CMD можно переопределить при запуске, не трогая логику подготовки:

ENTRYPOINT ["/usr/local/bin/entrypoint.sh"]
CMD ["node", "server.js"]
# обычный запуск — выполнится entrypoint.sh, а в конце CMD
docker run myapp

# переопределить CMD, entrypoint.sh всё равно выполнится первым
docker run myapp node debug.js
docker run myapp sh    # зайти в контейнер интерактивным шелом вместо запуска сервера,
                        # но ПОСЛЕ всех проверок из entrypoint.sh

5.3 Как аргументы CMD попадают в entrypoint-скрипт

Здесь замыкается связь с разделом 4: то, что записано в CMD (или передано после docker run image ...), Docker передаёт скрипту из ENTRYPOINT как обычные позиционные аргументы $1 $2 .... Задача скрипта — сделать свою работу, а затем передать управление этим аргументам как настоящей команде. Именно для этого нужна конструкция exec "$@" в конце entrypoint-скрипта:

#!/usr/bin/env bash
set -euo pipefail

echo "=== Подготовка перед запуском ==="
echo "Меня вызвали с аргументами: $@"

exec "$@"   # заменяет ТЕКУЩИЙ процесс bash процессом из аргументов, не порождая новый
💡 exec — это не "запустить", а "стать"

Без exec команда "$@" запустилась бы как дочерний процесс bash-скрипта, а сам bash остался бы висеть родителем и, что важнее, — оставался бы PID 1, а не ваше приложение. С exec процесс bash заменяется процессом приложения — тот же PID, но другой код внутри. Это не оптимизация, а необходимость: без неё сигналы остановки контейнера (раздел 2.4) будут приходить в bash, а не в ваше Node.js/PHP-приложение, и оно не узнает, что его просят завершиться.

5.4 Собираем полный пример

# Dockerfile

COPY package*.json ./

COPY . .
COPY entrypoint.sh /usr/local/bin/entrypoint.sh
RUN chmod +x /usr/local/bin/entrypoint.sh
ENTRYPOINT ["/usr/local/bin/entrypoint.sh"]

6. Тома и данные #

6.1 Проблема, которую решают volumes

Файловая система контейнера живёт ровно столько, сколько живёт контейнер: docker rm удаляет её безвозвратно вместе со всеми данными. Для базы данных это неприемлемо — данные должны переживать пересоздание контейнера (обновление образа, деплой новой версии). Docker решает это тремя механизмами:

ТипГде физически хранитсяУправляется Docker'омТипичное применение
Named volume/var/lib/docker/volumes/... на хостеда — создание, бэкап через docker volumeданные БД, которые не нужно трогать руками
Bind mountлюбой путь на хосте, который вы указали саминет — это просто путь на дискемонтирование исходного кода при разработке (live reload)
tmpfs mountоперативная память хоста, не дискдавременные секреты, кэш, который не должен пережить перезапуск
# named volume
docker run -v pgdata:/var/lib/postgresql/data postgres:16

# bind mount — абсолютный путь хоста слева от двоеточия
docker run -v /home/user/project/src:/app/src myapp

# то же самое современным флагом --mount (более явный, рекомендуется в документации Docker)
docker run --mount type=volume,src=pgdata,dst=/var/lib/postgresql/data postgres:16

6.2 Частая боль: несовпадение UID/GID

✅ Файлы созданы контейнером, но принадлежат root на хосте

Если процесс внутри контейнера работает от root (UID 0, по умолчанию — если не указан USER в Dockerfile), а с хоста через bind mount смонтирована папка — все файлы, созданные контейнером в этой папке, на хосте тоже будут принадлежать root. Для разработки это раздражает (нельзя редактировать файлы своим пользователем без sudo), а в проде — дополнительный риск безопасности. Решение — явно указывать непривилегированного пользователя в Dockerfile (USER node, как в примере раздела 3) или совмещать UID контейнера с UID хоста через --user $(id -u):$(id -g).

7.2 Своя bridge-сеть и DNS между контейнерами

Контейнеры в сети по умолчанию (docker0) видят друг друга только по IP, который к тому же может меняться при пересоздании. Решение — создать свою сеть: Docker поднимает в ней встроенный DNS-сервер, который резолвит имя контейнера (или имя сервиса в Compose) в его текущий IP:

docker network create lab-net

docker run -d --name postgres --network lab-net postgres:16-alpine
docker run -d --name app --network lab-net myapp
# внутри контейнера app можно обращаться к базе просто по имени:
#   psql -h postgres -U postgres
💡 Почему это работает, а на дефолтной сети — нет

Встроенный DNS Docker обслуживает только пользовательские сети (созданные через docker network create) — сеть bridge по умолчанию, в которую попадают контейнеры без явного --network, такого DNS не имеет по историческим причинам обратной совместимости. Отсюда практическое правило: всегда создавайте свою сеть для проекта из нескольких контейнеров — это ровно то, что Compose делает автоматически за вас (раздел 8), поэтому там имена сервисов "просто работают".

7.3 EXPOSE vs -p: документация vs реальность

EXPOSE 3000 в Dockerfile — это только метаданные, заметка "это приложение слушает порт 3000", она ничего не пробрасывает и не открывает. Реальный проброс порта с хоста на контейнер задаётся флагом -p при запуске:

docker run -p 8080:3000 myapp
#            │    │
#            │    └─ порт ВНУТРИ контейнера, тот самый, что слушает приложение
#            └─ порт НА ХОСТЕ, куда стучится браузер/curl

Если контейнеры общаются друг с другом внутри одной Docker-сети (пункт 7.2) — им проброс через -p не нужен вообще, они видят порты друг друга напрямую по внутренней сети. -p нужен только для портов, к которым должен обращаться мир снаружи Docker (браузер на хосте, внешний клиент).

8. Docker Compose #

8.1 Зачем Compose

Проект из двух и более контейнеров, поднятых вручную через docker run с кучей флагов сети, volume'ов и переменных — быстро становится нечитаемым и невоспроизводимым (легко забыть флаг). Docker Compose описывает весь стек одним YAML-файлом и поднимает/останавливает его одной командой.

8.2 Анатомия docker-compose.yml

services:
  app:
    build: .                     # собрать образ из Dockerfile в этой папке (вместо готового image:)
    ports:
      - "3000:3000"
    environment:
      - APP_NAME=DockerLab       # можно списком key=value...
      - DB_HOST=postgres          # ...или через отдельный map — см. 8.4
    depends_on:
      - postgres                  # ждёт СТАРТА контейнера postgres, но не его готовности — см. ниже
    networks:
      - lab-net

  postgres:
    image: postgres:16-alpine     # готовый образ из registry, без build
    environment:
      - POSTGRES_PASSWORD=labpass
    volumes:
      - pgdata:/var/lib/postgresql/data
    networks:
      - lab-net

volumes:
  pgdata:                          # объявление named volume — Compose создаст его сам

networks:
  lab-net:                         # объявление своей сети — DNS между сервисами работает "из коробки"

Команды: docker compose up -d поднимает весь стек в фоне, docker compose down останавливает и удаляет контейнеры (но не volumes — для этого нужен флаг -v), docker compose logs -f app — логи конкретного сервиса, docker compose ps — статус всех сервисов стека.

8.3 depends_on и healthcheck: "запущен" ≠ "готов принимать соединения"

💡 Самая частая причина "database connection refused" при первом старте

Обычный depends_on: - postgres гарантирует только порядок старта контейнеров: Compose запустит контейнер postgres раньше app. Но PostgreSQL внутри контейнера ещё какое-то время инициализирует базу данных после старта процесса — контейнер уже "запущен", а порт 5432 ещё не принимает соединения. Приложение стартует одновременно с этим окном и падает с ошибкой подключения. Именно поэтому entrypoint-скрипты с ожиданием готовности БД (шаг 2.3) — это не блажь, а необходимость. Compose может частично закрыть эту проблему сам, если у сервиса объявлен healthcheck:

services:
  postgres:
    image: postgres:16-alpine
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      timeout: 3s
      retries: 5

  app:
    build: .
    depends_on:
      postgres:
        condition: service_healthy   # ждать не старта, а именно "здорового" статуса healthcheck

condition: service_healthy заставляет Compose ждать, пока healthcheck не начнёт проходить успешно, и только потом стартовать app. Это снимает часть проблемы на уровне оркестрации, но не всю: между "healthcheck прошёл" и "приложение подключилось" всё ещё может быть гонка, поэтому bash-проверка внутри самого entrypoint'а (шаг 2.3) остаётся хорошей практикой как второй рубеж защиты.

docker-compose.override.yml подхватывается автоматически поверх основного файла и обычно хранит настройки только для локальной разработки (например, bind mount исходников для live reload), не попадая в production-конфигурацию. profiles: у сервиса позволяет исключать необязательные сервисы (например, Adminer для отладки БД) из обычного docker compose up, поднимая их явно через --profile debug, когда нужны.

Шаг 2.3wait-for-postgres.sh на bash#
#!/usr/bin/env bash
# app/entrypoint.sh — версия 3, с ожиданием БД
set -euo pipefail

DB_HOST="${DB_HOST:-postgres}"
DB_PORT="${DB_PORT:-5432}"
MAX_TRIES=30
TRIES=0

echo "Жду PostgreSQL на ${DB_HOST}:${DB_PORT}..."

until (echo > "/dev/tcp/${DB_HOST}/${DB_PORT}") 2>/dev/null; do
  TRIES=$((TRIES + 1))
  if [ "$TRIES" -ge "$MAX_TRIES" ]; then
    echo "PostgreSQL не поднялся за $((MAX_TRIES * 2)) секунд — выхожу." >&2
    exit 1
  fi
  echo "  ...ещё не готов (попытка $TRIES/$MAX_TRIES)"
  sleep 2
done

echo "PostgreSQL доступен. Стартуем приложение."
exec "$@"
🐚 BASH

/dev/tcp/HOST/PORT — это не настоящий файл, а специальная возможность самого bash (не POSIX-стандарт, не работает в sh/dash): перенаправление в этот "путь" открывает обычное TCP-соединение. Именно ради таких вещей в разделе 3.6 выбран node:20-slim с настоящим bash, а не Alpine со скудным sh. Цикл until (...) 2>/dev/null; do ... done — конструкция из раздела 4.4: "повторять, пока условие ложно"; 2>/dev/null глушит ожидаемые ошибки "соединение отклонено" на каждой неудачной попытке, чтобы не засорять логи.

💡 Почему без exec остановка "зависает" на 10 секунд

docker stop посылает SIGTERM процессу PID 1 и ждёт (по умолчанию 10 секунд) его корректного завершения, после чего принудительно убивает через SIGKILL. Без exec PID 1 — это сам bash-скрипт, а node — его дочерний процесс. Bash по умолчанию не пересылает полученные сигналы дочерним процессам автоматически, поэтому node просто не узнаёт о запросе на остановку — Docker ждёт истечения тайм-аута и убивает всё жёстко через SIGKILL, минуя graceful shutdown приложения (незакрытые соединения с БД, недописанные логи).

Верните exec обратно — это правильное поведение по умолчанию для 95% entrypoint-скриптов. Но иногда нужно и своё действие по сигналу (например, сначала аккуратно закрыть соединения, потом выйти) — для этого существует trap:

#!/usr/bin/env bash
set -euo pipefail

cleanup() {
  echo "Получен SIGTERM, останавливаю дочерний процесс..."
  kill -TERM "$child" 2>/dev/null || true
  wait "$child"
  echo "Дочерний процесс завершён, выхожу."
}

trap cleanup SIGTERM SIGINT

"$@" &
child=$!
wait "$child"
Зачем такая альтернатива exec: здесь bash сознательно остаётся PID 1 (никакого exec), запускает команду в фоне (&), запоминает её PID ($!) и ждёт (wait). trap cleanup SIGTERM SIGINT перехватывает сигналы и выполняет свою функцию вместо стандартного поведения. Это сложнее и нужно редко — предпочитайте простой exec "$@", пока реально не понадобится что-то сделать между сигналом и завершением процесса.

  1. Порт наружу. curl http://localhost:3000 не отвечает, хотя контейнер поднят: приложение слушает 3000 внутри, а проброшен 8080:внутри. Правило раздела 7.3 — проброс пишется хост:контейнер, тут перепутан порядок. Чинится на "3000:3000".
  2. Имя хоста БД не совпадает с именем сервиса. DB_HOST=postgresql, а сервис в Compose называется db — DNS раздела 7.2 резолвит имена сервисов, а не произвольные строки. Чинится на DB_HOST=db (или сервис переименовывается в postgresql — главное, чтобы совпадало).

  4. Неверный путь volume внутри контейнера Postgres. Официальный образ postgres хранит данные в /var/lib/postgresql/data (с ql), а в compose-файле опечатка — /var/lib/postgres/data. База данных инициализируется каждый раз заново в невидимом слое контейнера, будто volume не работает вовсе — данные физически не там, где вы их монтируете.
  5. depends_on без healthcheck при этом наборе ошибок маскирует происходящее. Даже почини́в имя хоста, без condition: service_healthy (раздел 8.3) есть шанс словить гонку при первом холодном старте — добавьте healthcheck для db, как в шаге 3.1.

  • Контейнер vs виртуальная машина: общее ядро хоста, namespaces и cgroups как основа изоляции.
  • Образ vs контейнер vs Dockerfile vs registry — и что из этого неизменяемо, а что имеет состояние.
  • Слои и кэш сборки: почему порядок инструкций в Dockerfile напрямую влияет на скорость пересборки.
  • Build context и .dockerignore; почему секреты нельзя копировать в образ через COPY . ..
  • RUN — это время сборки, CMD/ENTRYPOINT — это время запуска контейнера.
  • Shell form vs exec form; почему exec form почти всегда правильный выбор.
  • ENTRYPOINT + CMD как связка "скрипт-обёртка + переопределяемая команда".
  • exec "$@" — зачем нужен именно exec, а не просто запуск команды.
  • PID 1 и обработка сигналов: почему без exec docker stop "зависает" на таймауте.
  • Bash: переменные и кавычки, test/[[ ]], циклы, функции, local.
  • set -e, set -u, set -o pipefail — что каждый из них ловит.
  • Позиционные параметры и разница между "$@" и голым $@.
  • Named volume vs bind mount vs tmpfs — когда что использовать.
  • Своя bridge-сеть и встроенный DNS Docker: почему имена контейнеров резолвятся только в пользовательских сетях.
  • EXPOSE — это документация, -p — это реальный проброс порта.
  • depends_on vs depends_on + healthcheck: порядок старта контейнеров ≠ готовность сервиса.
  • Multi-stage build: как убрать инструменты сборки и devDependencies из финального образа.
  • restart policies и лимиты ресурсов (cgroups на практике через Compose).

11. Глоссарий терминов #

Образ (image) — неизменяемый слепок файловой системы + метаданные о запуске; хранится слоями.

Контейнер (container) — запущенный или остановленный экземпляр образа: реальный процесс со своим ID и состоянием.

Слой (layer) — неизменяемый diff файловой системы, созданный одной инструкцией Dockerfile; кэшируется и переиспользуется между образами.

Namespaces — механизм ядра Linux, ограничивающий, что процесс видит (свою сеть, свои процессы, свою файловую систему).

Cgroups — механизм ядра Linux, ограничивающий, сколько ресурсов (CPU, память) может использовать процесс.

Build context — папка, целиком отправляемая демону перед сборкой; источник файлов для COPY/ADD.

.dockerignore — файл, исключающий пути из build context, аналог .gitignore.

ENTRYPOINT — основная программа образа, которая запускается всегда; обычно скрипт-обёртка с проверками.

CMD — аргументы или команда по умолчанию, легко переопределяемая при docker run.

Exec form — запись команды JSON-массивом (["node","server.js"]), выполняется без промежуточного шела.

PID 1 — первый процесс в пространстве имён процессов контейнера; получает сигналы остановки напрямую от Docker.

exec (bash) — встроенная команда bash, заменяющая текущий процесс новым, без порождения дочернего.

Shebang — первая строка скрипта (#!/usr/bin/env bash), указывающая интерпретатор.

Exit code — числовой код завершения команды (0 — успех), доступен в bash через $?.

set -euo pipefail — три флага bash: остановка при ошибке, ошибка при необъявленной переменной, провал всего конвейера при провале любой команды в нём.

trap — команда bash, назначающая обработчик на получение сигнала (например, SIGTERM).

Named volume — управляемое Docker'ом постоянное хранилище данных, переживающее удаление контейнера.

Bind mount — монтирование произвольного пути хоста внутрь контейнера напрямую.

Bridge network — виртуальная сеть Docker; пользовательская bridge-сеть даёт встроенный DNS по именам контейнеров.

Healthcheck — периодическая проверка готовности сервиса, используемая для depends_on: condition: service_healthy.

Multi-stage build — Dockerfile с несколькими FROM, где финальный стейдж копирует только нужные артефакты из предыдущих.
